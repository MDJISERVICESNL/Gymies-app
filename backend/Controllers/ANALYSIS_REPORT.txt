CRITICAL BUGS & SECURITY ISSUES
================================

1. RACE CONDITIONS IN FINANCIAL TRANSACTIONS (CRITICAL)
   Location: waiveTrainerPenalty (line 1323), refundOrCredit (line 1360),
             bulkRefundToWallet (line 1491), resolveIncident (line 1745)

   Issue: Non-atomic read-modify-write operations on user balances:
   - Line 1342-1345 (waiveTrainerPenalty):
     $current = DB::table('gymies_users')->where('id', $trainerId)->value('trainer_balance_cents');
     $newBalance = $current + $addCents;
     DB::table('gymies_users')->where('id', $trainerId)->update(['trainer_balance_cents' => $newBalance]);

   - Line 1433-1435 (refundOrCredit):
     $currentBalance = DB::table('gymies_users')->where('id', $clientUserId)->value('wallet_balance_cents');
     $newBalance = $currentBalance + $amountCents;
     DB::table('gymies_users')->where('id', $clientUserId)->update(['wallet_balance_cents' => $newBalance]);

   - Line 1522-1524 (bulkRefundToWallet):
     Same pattern in loop - multiple concurrent admins could lose data

   - Line 1788-1790 (resolveIncident):
     Same pattern - balance += amountCents

   IMPACT: Two simultaneous balance updates could result in losing one transaction.
           Example: Balance = 100. Admin1 adds 50 (reads 100, writes 150).
           Admin2 adds 25 (reads 100, writes 125). Result: 125 instead of 175.

   FIX: Use atomic DB::increment() / DB::decrement() or DB::transaction() with pessimistic locking

   SEVERITY: CRITICAL (financial data loss)


2. MISSING VALIDATION ON FINANCIAL AMOUNTS (CRITICAL)
   Location: refundOrCredit (line 1360), cancelBooking (line 1278)

   Issue: Insufficient validation on amount_cents:
   - Line 1400: amount_cents can be null, defaults to booking amount
   - Line 1408-1409: Only validates amount_cents > 0 for 'partial_refund' type
   - Line 1414-1415: Caps to booking amount but no minimum validation
   - No check for negative amounts in request
   - Line 1419: getSetting('bank_refund_admin_fee_cents') is unchecked string

   Example attack:
   - Send amount_cents: -100000 (negative)
   - System accepts it if validation is weak
   - Trainer balance could be subtracted instead of added

   FIX: Add explicit validation:
        $request->validate(['amount_cents' => 'required|integer|min:1|max:5000000']);

   SEVERITY: CRITICAL (financial manipulation)

4. UNVALIDATED STRTOTIME() IN RED FLAG DETECTION (HIGH)
   Location: inboxRedFlags (line 2954)

   Issue: Non-strict date comparison:
   - Line 2954: (strtotime($d) - strtotime($prev)) <= 86400 * 2
   - $d and $prev come from database cancelled_at fields
   - If date format is inconsistent, strtotime() could fail silently (returns false)
   - false - false = 0, could match <= 86400*2 (true) unexpectedly

   FIX: Use Carbon parsing instead:
        Carbon::parse($d)->diffInSeconds(Carbon::parse($prev)) <= 86400 * 2

   SEVERITY: HIGH (logic bug in flag detection)


5. SQL INJECTION VIA LIKE QUERIES (MEDIUM - MITIGATED)
   Location: users() line 135-145, search() line 338-340, audits() line 475-477

   Analysis: LIKE queries with user input:
   - Line 135: $w->where('email', 'like', "%{$q}%")
   - Input $q is from $request->query('q', '') - trimmed but not parameterized

   Status: Laravel's query builder parameterizes the % wildcards, so injection is
           actually prevented. The pattern "%{$q}%" is safe because Laravel escapes
           the variable before passing to DB driver. However, code style suggests
           developer may not realize this.

   Better style would be explicit parameterization:
        ->where('email', 'like', DB::raw('?'), ["%{$q}%"])

   SEVERITY: MEDIUM (mitigated by framework but poor practice)


6. NO IDEMPOTENCY PROTECTION (HIGH)
   Location: All refund/credit/payment operations

   Issue: POST requests modifying balances are not idempotent
   - refundOrCredit (line 1360): No check if refund already exists
   - waiveTrainerPenalty (line 1323): Could add penalty multiple times
   - bulkRefundToWallet (line 1491): No deduplication

   FIX: Add idempotency key validation or unique constraint on (booking_id, admin_id, action)

   SEVERITY: HIGH
